# 任务 07（重写版）：让 Hermes 在这个环境里越来越可靠

> 原题：「全网查怎么让 hermes 越来越好用」。原题太大、太软、无法验收。
> 下面按四问重写：专家会补什么、从什么原始材料入手、用什么方法、拿什么证明。

---

## 一、顶尖专家会做、而原题没要求的事

1. **先定义"好用"，再动手。** 原题里的"好用"是感觉。专家会先写死四个指标：
   任务一次成功率、返工率（被用户纠正的次数/任务数）、同类错误重复率、单任务成本。
   没有基线就没有改进，只有安慰。
2. **读源码，不读二手解读。** Hermes 的 SOUL/SKILL/memory 究竟按什么顺序拼进系统提示、在哪一层被截断、
   cron 会话和聊天会话差在哪——这些只在源码里，社区文章只会说"要精简"。
3. **建最小失败集，而不是写长文档。** 从真实日志抽失败样本，做成可重跑的用例；
   文档会腐烂，用例不会。
4. **每次改动做对照。** 同一批用例，改前跑一次、改后跑一次，**同一模型、同一参数**，比较通过率。
   样本不足就明说"不足"，不许用感受代替差异。
5. **把"不能做"放进机制。** 提示词约束不了模型，denylist / hook / 独立看门狗才行。
6. **成本与延迟分层。** 确定性的活给脚本（零 token），判断类活才给模型，且按任务钉不同模型。
7. **可回滚。** 所有配置入 git，改动带症状/证据/验证三元组，坏了能 revert。
8. **监控生产，不监控心情。** 402、超时、静默失败、任务连续失败，全部进可查询的表，出趋势图。

## 二、从哪些最原始的材料入手（而不是别人嚼过的）

| 材料 | 位置 | 为什么是"原始" |
|---|---|---|
| Hermes 源码 | `~/.hermes/hermes-agent/`（prompt 装配、skill 加载、cron runtime、memory 注入） | 决定行为的真实代码，不是文档承诺 |
| 官方 spec / reference | `hermes-agent.nousresearch.com/docs/reference`、skills 规范 | 一手定义 |
| 本机日志 | `~/.hermes/logs/errors.log`、`logs/sessions/*.jsonl`、`cron/executions.db` | 真实发生了什么 |
| 我们自己的留痕 | `~/repos/hermes/evals/runs.jsonl`、`cases.jsonl`、`report.json` | 真实失败与真实判据 |
| 论文原文 | arXiv 全文（2608.02639、2610.11007、Chroma context-rot） | 数字与条件，不看转述 |
| 用户原话 | 聊天记录（session_search） | 唯一权威的需求来源 |

## 三、具体方法与工具

1. **prompt 装配溯源**：源码里 grep `SOUL`、`skills`、`memory` 的注入点，画出真实顺序与截断规则。
2. **用例集分层扩充**：20 → 50 条。来源：30 天真实对话抽样 16 条 + 历史事故 10 条 + 对抗 8 条 + 边界 16 条。
3. **A/B 对照**：`evals/run.py` 固定模型与参数，改前/改后各跑一遍，记录 passed/failed 明细。
4. **日志结构化**：把 `errors.log` 解析进 SQLite，按天/按模块聚合，出"同类错误重复率"趋势。
5. **变更管理**：每次改 SOUL/SKILL/AGENTS 前 `git commit`，commit message 写症状/证据/验证；坏了 `git revert`。
6. **成本核算**：按任务类型统计 token 与费用（`hermes usage` + cron 执行记录），找出最贵的三类任务。
7. **夜间外层循环**：23:30 cron 读 runs → 只改有 ≥2 次证据的一条 → 写理由。
8. **红色门禁**：eval 通过率下降就推送告警，不许静默。

## 四、除了你我，还有什么能证明结果是对的

1. **eval 通过率**：机器判据（tool_called / pattern_present 等），跑出来的数字，不是我说好。
2. **同类错误重复率**：30 天内同一错误出现次数，降了才算改对。
3. **返工率**：你说"不对/重做"的次数 ÷ 总任务数，可从聊天记录统计。
4. **可复现性**：任何人用同一命令、同一用例集、同一模型，能跑出同样结果。
5. **配置差异**：改动前后 SOUL/skill 的 sha256 + eval 报告，成对存档。

## 重写后的任务（可执行版）

**目标**：在 30 天内，把「同类错误重复率」降到当前的一半，同时 eval 通过率 ≥80%。

**第 1 周（测基线，不改任何规则）**
1. 读源码，画出 SOUL/skill/memory 的真实注入顺序与截断点，写成 `notes/prompt-assembly.md`。
2. 用例集扩到 50 条，每条自带上下文、判据只看行为。
3. 修好跑分器的会话发现与 `--only` 重复传参。
4. 全量跑一次，得到**基线通过率**，存为 `evals/baseline.json`。

**第 2 周（结构化日志 + 只改一处）**
5. `errors.log` 解析进 `~/.hermes/state/incidents.db`，按天出同类错误计数。
6. 只改**证据 ≥2 次**的那一条规则（优先改 skill，其次 AGENTS，最后 SOUL），跑对照。
7. 夜间外层循环上线（已在 23:30 cron）。

**第 3–4 周（对照 + 门禁）**
8. 每周跑一次全量 eval，与 baseline 对比，记录差异与置信度（样本不足就说不足）。
9. 通过率下降则推送告警；连续两周无改进则停手，写出「哪条假设被证伪」。

**验收**：baseline.json、eval 报告（改前/改后成对）、incidents.db 的趋势、以及一句明确结论：
「哪条规则被证明有用、哪条被证明无用」。

**不做**：不加新规则除非有 ≥2 次证据；不改交易代码；不动钱。
