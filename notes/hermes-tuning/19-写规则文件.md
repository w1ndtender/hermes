# 19 怎么写规则文件（AGENTS.md / SOUL.md）——带研究依据

来源：betterclaw《AGENTS.md Best Practices》（引 Anthropic 文档、GitHub 对 2500+ 个
agents.md 的分析、arXiv 2605.10039 的 1650 次会话对照实验）、stanza 课程、
michaelcostea 的公开 starter pack、Reddit「五种长期记忆方案」实测帖。

## 一、长度：目标 <100 行，常见 30–80 行
- Anthropic 自己的上限是 200 行；社区共识是 100 行以内，超过 150 是警告信号。
- 研究结论（arXiv 2605.10039，1650 次会话）：单条规则的遵守率**跟文件长度、位置、
  是否拆分都没显著关系**；真正相关的是任务本身和**会话进行到多深**——
  每多写一个函数，遵守该规则的几率下降约 5.6%。
- 另一组结论：上下文文件整体「不明显提高成功率，但平均增加 20%+ 推理成本」。
- 结论：短文件救不了烂任务，长文件一定让每个任务更贵、更容易漏掉关键那条。

## 二、该写什么（按顺序）
1. **技术栈**（5–10 行）：语言、框架、主要依赖、运行时，要具体。
2. **构建与测试命令**（5–10 行）：带完整参数的原文，别写「按 package.json 来」。
3. **代码风格**（10–20 行）：**每条给一个例子**，一个例子胜过三段描述。
4. **架构约束**（5–15 行）：目录规则、模块边界、禁止的 import。
5. **禁区**（5–10 行）：「绝不提交密钥」是 GitHub 统计里最有用的一条；
   再加生成目录、遗留模块、别人管的配置。
6. **Git 约定**（5 行）：分支名、提交信息格式。

## 三、不该写什么
- **多步流程**（发版清单、迁移手册）→ 放 skill，用的时候才加载。
- **工具怎么连**（MCP、API key）→ 属于工具配置，不属于规则文件。
- **必须强制执行的事** → 用 hook / 权限规则，不要靠文档「求它」。

## 四、规则的生命周期（保持长期不腐坏）
1. 起步 30–50 行。
2. **只有同一个错犯第二次才加规则**（一次可能是任务本身的问题）。
3. 规则写成「约束 + 例子」，不要写成解释。
4. 几周或换模型后，删掉这条再跑同类任务；模型自己能做对，这条就是死重。
5. 每季度通读一次，规则变更时同一个 PR 里改。

自检一句：**一个从没见过这个仓库的合格工程师，会不会做错这条？**
不会 → 删掉，你只是在把它本来就会的事重复收费。

## 五、矛盾比重复更糟
官方原文：两条指令冲突时，模型可能**任选一条**。冲突常藏在：
根目录与子目录规则、个人全局规则与项目规则、迁移后没删的旧规则、规则与其例外分处两节。

## 六、硬上限：写太长会被截断
Hermes 对超大上下文文件会截断，**中间那部分会静默消失**。
20K 字符以上的文件要当作已经坏了。

## 七、记忆解决不了「下一步做什么」
Reddit 那位实测五种方案后的结论（值得抄）：
- 手写项目笔记：会忘记更新；
- AGENTS.md：适合稳定约定，不适合活的状态；
- `/compress`：记住「发生了什么」，记不住「还差什么」；
- 外部记忆服务：什么都能查，但不会推动下一步；
- 一个巨型会话：只是拖后问题。

他最后用的是「项目状态文件」：任务、负责人、产出、卡点可见，**只在值得做的时候提示下一步**。

**对我们的直接结论**：除了 AGENTS.md，还该有三份小文件——
`STATUS.md`（当前状态与下一步）、`DECISIONS.md`（拍过板的决定和理由）、
`HANDOFF.md`（交接给 Codex 或下次会话的东西）。
