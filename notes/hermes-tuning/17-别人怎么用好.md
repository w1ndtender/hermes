# 17 别人怎么把 Hermes 用好（官方 User Stories 精选 + 归纳）

来源：官方 `docs/user-stories`（社区真实帖子汇总，X/Reddit/HN/LinkedIn/GitHub），
以及 Neogen、DEV、Reddit 的复盘文。

## 一、六种被验证有效的模式

### 模式 1：两层架构 —— 便宜的哨兵 + 贵的脑子
- 原文案例：Tier 1 用脚本检测新邮件/状态变化；Tier 2 只在「有新的」时才起 LLM 会话。
- 另一个版本：「brain-and-arm architecture」（脑子决策、胳膊执行）。
- **映射到我们**：脚本每 N 分钟抓盘口/链上，命中条件才让模型写人话推送。
  这是最该抄的一条，直接解决「贵」和「结论不稳定」。

### 模式 2：多源交叉，不信单一数据
- 交易案例：$100 → $216 / 48 小时。做法是**每 60 分钟扫一次天气市场，
  对每个地点比对 3 个预报源**，只买被低估的温度档。
- **映射到我们**：价格/价差/池深必须两个来源对齐（DexScreener + 链上/交易所），
  对不上就不出手 —— 这正是我们之前算错价差的反面。

### 模式 3：一个角色一个 agent，各自有 guideline
- 单人创业做 7 个助手：增长分析（接 PostHog）、SRE（接 Better Stack）、
  幕僚长（接 Linear）、内容、客服等；每个只干一件事，各自有规则文件。
- IT 支持 agent 靠一份 guideline 自己解决 90% 工单。
- **映射到我们**：不必 7 个 profile，但可以把「盯盘 / 研究 / 记账」三件事的规则分开写，
  别混成一个万能提示。

### 模式 4：审批闸 + 每日固定产出
- 营销创始人：WhatsApp 回复、审批后才执行的任务、Notion 打卡；
  原话「两周下来这是我今年最好的招聘」。
- SEO 那位：每天检查分析数据、写内容、**等你批准**再上线。
- **映射到我们**：下单前审批（已做）、每天固定时间给一份「今天该看什么」。

### 模式 5：研究型 agent 会「记仇」——记录你忽略了什么
- 有人让 agent 盯 AI 领域信号、写简报、推荐选题，**并记录自己忽略过什么**，
  下次不再推荐同样的东西。
- **映射到我们**：推送被忽略的标的要标记，避免天天重复推同一条无效机会。

### 模式 6：把难啃的大材料落到本地结构化存储，别塞上下文
- 有人把 3799 页 AMD 手册解析进 SQLite FTS5，而不是向量库：
  「直接把大文件塞进上下文会炸」。
- **映射到我们**：历史成交、链上事件、看板快照都进 SQLite/JSONL，用查询代替「全读一遍」。

## 二、几个可直接照搬的小习惯

- **一个订阅跑全队**：GTM 团队用一台 VPS + 一个 Hermes 订阅给全组用，
  比每人一个 coding seat 省约 $800/月。→ 我们已经在这么用。
- **Telegram 当遥控器**：多个案例都是「在 Telegram 里说一句，agent 去集群上干活，
  干完回消息」。→ 我们已具备，缺的是「干完自动回报」。
- **28 个 cron + 凌晨 3 点的「做梦」任务**：半夜整理当天上下文、写第二天要用的摘要。
  → 我们可以做「每晚把当天成交/信号整理成一条，供第二天判断」。
- **把 PDF/截图丢进 Telegram 就出 PR**：说明「输入形态不重要，落地产物才重要」。

## 三、反过来的教训（他们也踩过）

- 上下文塞太大 → 一定要外部存储 + 检索。
- 单个万能 agent 干活越来越飘 → 拆角色、拆规则。
- 没有审批闸的自动化，出事时没人知道是哪一步错的。

## 四、我们下一步最该抄的三条

1. **两层架构**：脚本哨兵 + 模型只在有情况时写人话（省钱、结论稳定）。
2. **多源交叉**：任何价格/价差数字，两个独立来源对不上就不出手。
3. **夜间整理**：每天 0 点把当天信号与成交落成一条结构化摘要，替代每天早上现算。
