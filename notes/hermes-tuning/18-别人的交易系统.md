# 18 别人用 Hermes 做交易的架构（真实开源案例）

来源：GitHub `Gabriel-0110/.hermes` 的 `docs/architecture/hermes-trader-architecture.md`
（一套多 agent 加密交易平台的架构文档，2026），以及 DEV 上那篇 IBKR 量化复盘。

## 一、唯一值得抄的骨架：控制流

```
行情/信号 → 风控与策略判定 → 审批与模式闸 → 执行 → 观测与持仓状态
```

拆开是九步：
1. 研究 agent 建立市场上下文
2. 策略 agent 提出候选机会
3. 持仓监控 agent 查当前敞口
4. 编排 agent 合成交易意图（proposal）
5. 风控 agent 通过或否决
6. 执行连接器下单
7. 数据库把 proposal / 审批 / 订单 / 成交 / 资金变动全部落库
8. 仪表盘可视化
9. 通知分发

**和我们的差别**：我们是「信号 → 直接下单 → 事后算账」，中间的风控闸、模式闸、落库、可视化全缺。
今天亏 $32 不是策略问题，是这四步缺失的直接结果。

## 二、六种运行模式（必须先声明自己在哪种）

研究模式 / 建议模式 / 纸面交易 / 人工审批 / 半自动 / 全自动。

**我们现在连「在哪种模式」都没写清楚** —— 说是人工审批，实际执行器在自动开平。
规矩：任何时刻只能是一种模式，写在配置里，且执行器启动时打印出来。

## 三、13 类共享资源（当 checklist 用）

1. 行情价格（现价/历史 OHLCV）
2. 盘口深度（买一卖一、失衡）
3. 逐笔成交（主动买卖、大单）
4. 技术指标引擎
5. 衍生品数据（资费、持仓量、基差、爆仓区）
6. 账户与持仓状态
7. **风控策略引擎**（仓位上限、亏损上限、最大回撤、熔断、审批闸）
8. 策略库（可复用剧本）
9. 新闻/情绪
10. 链上情报（钱包流、交易所进出、解锁）
11. 执行连接器（下单/撤单/成交回报）
12. 记忆与知识库（历史决策、复盘）
13. 预测/时序引擎

**对照我们**：
- 有：1（部分）、2、5（部分）、10、12（刚起步）、11（只有 Bitget/SafeTrade/HL）
- 缺：3、4、**7（最关键的缺口：没有独立风控引擎）**、8、9、13

## 四、三条设计原则（他们说得很直白）

1. **单一运行时真相**：状态只有一个来源，其他都是视图。我们相反 —— 权益有 3 个算法。
2. **共享智能层**：外部数据先标准化成工具/技能，agent 不各自抓原始数据。
   我们是每个脚本自己抓、自己解析 → 同名不同币、稳定币算错价。
3. **执行与推理分离**：agent 只产出 intent，执行、去重、审计由服务层做。
   我们是 agent 直接调下单函数。

## 五、他们的诚实之处（值得学）

文档原话大意：这套东西「不应被读作已完全统一或生产成熟」，执行能力「有限且受控」，
队列层「仍然轻量或仍在成型」。**不吹**，把没做完的部分写清楚。

## 六、对我们要做的事（不改代码，只改流程）

1. 先写死「当前模式」：纸面 / 人工审批（二选一），执行器启动必须打印。
2. 补一个独立风控闸：不通过就不许下单（不是执行器内部判断）。
3. 所有成交与决策落一张表：proposal → 审批 → 订单 → 成交 → 盈亏，一条链可追。
4. 权益与价差各自只能有一个计算入口（我们已经对价差做了，权益还没）。
