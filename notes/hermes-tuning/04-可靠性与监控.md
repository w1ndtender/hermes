# 04 可靠性：静默失败是头号杀手

## 别人的教训
一家公司在生产跑一个月：4 个 agent、36 个 cron，出现过**六天静默停机**。
四条硬结论：
1. 容器/服务必须以正确模式常驻，否则开机即退。
2. 每个 agent 独立容器与 UID，否则凭据隔离是假的。
3. **每个 cron 必须钉模型**，否则供应商一换就静默死。
4. **每个静默失败都要有计数器**。

## 我们身上的实例
- `agent-daily-brief` 上次 **idle 7943 秒后超时失败**，错误只在 cron 历史里。
- 抓数据的脚本里 `except: pass` 把接口失败当「没有数据」。

## 做法
- 每任务写一行结构化日志：`{任务, 时间, 成功/失败, 条数, 耗时}`。
- 一天一条汇总；**只有异常才推**。
- 用 `hermes cron doctor` / `incidents` 定期看一眼。
- 超时设置要显式给，不要靠默认值。


## 补充（2026-11-04 实测）：断粮与备胎

- **默认没有备胎。** 配置项是 `fallback_providers: [{provider, model}]`（代码里有实现：主 provider 失败会 swap 到 fallback client）。只有主 provider 凭据时，一次 402 就全线停摆。
- **402 不是"慢"，是"没钱"。** 日志里表现成 `Streaming failed before delivery: Error code: 402 - Insufficient Balance`，上层看到的是超时/流中断，很容易误判成网络问题。
- **余额要当健康指标。** DeepSeek 有公开端点：`GET https://api.deepseek.com/user/balance`（Bearer 主 key），返回 `total_balance`。低于阈值该推一条。
- **网关会自杀重启。** `gateway.shutdown_watchdog` 在事件循环连续 3 次心跳失败后 dump 线程栈并 exit 75，由 systemd 拉起——这是保护，不是崩溃，但期间 cron 会卡住（实测 7943 秒）。
- **噪音要会滤。** 7 天 3325 条 WARNING 里，绝大多数是 SQLite 版本提示、未知配置键、无 MCP 连接；真正要看的是 ERROR/CRITICAL（83 + 1）。
